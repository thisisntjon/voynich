### 2b. Collision risks with four concurrent sessions

1. **Results-file overwrite by prefix reuse (realised).** `p1_order_sensitivity.py` (TOP10 #5) and `p1_bifolio_null.py` (handoff tier-1 #4) both write `results_p1.txt`; the bifolio null's Parts A–D are gone from disk. Fix (one line, outside my scope): rename the order-sensitivity output to `results_p1b.txt` or `results_s0.txt` and re-run `p1_bifolio_null.py` to restore the cited file (its hash `3aba99a6…` is recorded, so the rerun is reproducible). Rule for the wave plan: a session claims a prefix in `TEAM-HANDOFF.md` "Prefixes" **before** writing the script, and `TOOLS.md`'s register says the next free block is `s1` onward; this doc assigns `s1`–`s16` and `t1` below.
2. **`scoreboard/scoreboard.json` read-modify-write.** n6 and n7 (both via `run_v2.py`) plus any `run.py` call in Phase 2 will each load-then-write the whole file; concurrent runs silently drop each other's entries, and `score.py main()` truncates it. Mitigation: each session writes `runs/<prefix>/board.json` and one designated session merges; or `run_v2.py --out` per session.
3. **The `controls_synthetic` glob.** Phase 2a/2b and the gibberish build drop sidecars that m4/n5-style boards will pick up on their next run and silently add to a family range (name-prefix rule). A sidecar written mid-run (k5 `write_text` of a multi-MB JSON) can also be read half-written by a board starting at the same moment. Mitigation: write to `runs/<prefix>/` then move; new families go in their own directory (`data/controls_gibberish/` as the baseline plan says).
4. **Memory.** 3.8 GB free of 32 GB at 19:21, with n5 at 230 MB. m4-class runs (47 corpora through NMF + bake-off, holding every corpus's pages and the whole log in memory) are the ones that died. NMF (`sklearn`) and `TfidfVectorizer` in `b5`/`c1`/`p1`/`n3`/`n4` are the heavy allocators; `i1`/`j*` KMeans jobs are the other class. **Cap: at most 3 python experiment processes at once, at most 1 of them board-scale (m4/n5/n7/Phase-2 scoring) and at most 1 NMF-bootstrap job (n4/p1/O-001/O-028) at the same time; the fourth session does doc/sourcing work.** Order within a wave: start the longest job first (n4), then the board-scale job, then light jobs.
5. **Module patching.** `c2_section_generator` patches `b4.build_neighbours` at import; b4 SIMcal output depends on `PYTHONHASHSEED`. Any Phase 2 generator that imports both must import c2 after b4 generation and set `PYTHONHASHSEED` in its run line, or its hash-pinned rerun will not reproduce.
6. **Two writers for one results file by design:** `ctl_generators.py` and `ctl_report.py` both write `results_ctl_generators.txt`; `scoreboard/run_new.py` writes `results_m0_newmetrics.txt` under an old header. Not on the wave path, but do not rerun either while a board reads them.
7. **Runtime mixing.** `uv run` (3.13, scikit-learn >= 1.9.1) vs system 3.11 (sklearn 1.8.0): NMF/KMeans numerics can differ across sklearn versions; a stub must name the interpreter, and a hash-pinned rerun must use the same one.

## 3. Pre-registration stubs (n2/n3 pattern)

Pattern used by n1–n5: the stub is the module docstring, headed `PRE-REGISTRATION (written <clock stamp> before any run of this file; nothing below is changed after results are seen)`, listing texts, measures with the unchanged code they call, the decision rule with numeric thresholds and a fixed interpretation, and `Run: python <file> -> results_<prefix>.txt`.
