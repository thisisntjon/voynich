## 2. vparse finding

- The repo `vparse.py:10,31` has `DATA = .../data/ZL3b-n.txt` and `def load(strict_spaces=False, path=DATA)`. A call with no arguments loads ZL3b by design. db-S136's own prereg (`:17`) says to use ZL3b through `vparse.load()`. There is no `tools/vparse*`.
- **The actual trap is positional.** The first argument is `strict_spaces`, so `vparse.load(str(path))` sets `strict_spaces` to a non-empty string. That is truthy, so commas are deleted instead of splitting words. `path` then stays ZL3b. The bug therefore does two things silently: it loads ZL3b for every transliteration, and it changes how word breaks are read.
- **It happened in Pillar 5 itself.** The first version had `return vparse.load(str(path))`. Argon's tool diff at step 1734 (20:20:53) shows the only edit: `-    return vparse.load(str(path))` / `+    return vparse.load(path=path)`.
- The pre-fix run (task-1722, 20:19:41) printed **identical numbers for ZL3b, RF1b and IT2a**: 109 stems, 15 x 51, rank-3 .99340364, MI .97005. So it was ZL3b three times, with strict spaces. The fixed run gave 69/76/65.
- No later version of the 109 figure was found in `<team-comms>`. Whether it reached any chat is unverified.
- **Earlier Argon "3-transliteration" claims are not affected, by code inspection.** I grepped every `.py` under the repo, `codex_lab` and `.gemini\antigravity\brain` for positional `vparse.load(<arg>)`. There are 0 hits: every argument call uses `path=` or `strict_spaces=`. I also found no `vparse.DATA =` patch. That patch would not work anyway, because the default is bound when the function is defined.
- Per script, the RF1b/IT2a data enters as follows:
  - Pillars 1-2: Daybreak's own `parse(tpath)` / `parse_ivtff(tpath)`. Outputs differ by transliteration, for example S128 n 886/894/887 and r .0652/.0520/.0590.
  - Pillars 3-4: the VKB `tokens` table keyed by `translit` (39,020/38,525/37,919 tokens).
  - `vparse.load()` is used only for ZL3b-only parts: pillar4 4A, the db-S136 extension, s35, s38 boxes/f57v, s66 boxes.
  - s60/s73/s75/s77 etc.: `data/translit/*.meta.json` sidecars (distinct hashes), raw IVTFF parsers, or `vparse.load(path=...)` (s34, s51, s70).
- **One mislabel remains.** The docstring of `exp_dbs136_fast_and_allograph.py:5` says "3-transliteration", but the code calls `vparse.load()`, which is ZL3b only. Audit D already noted that there are no RF1b/IT2a cells.
- What would refute this: a Pillar 1-4 or s-run output whose RF1b/IT2a numbers equal ZL3b to every digit. I spot-checked pillar1 and pillar4 and they differ. I did not diff every `results_sNN` per-transliteration block, so that part is unverified.
